# 使用与兼容说明

## 共享推送与应用接入

Pixel MiPushFramework 为接入小米推送的应用提供共享服务，减少各应用分别维持推送连接的需要。目标应用是否接入，仍取决于它集成的 SDK、设备识别逻辑和系统限制。

框架与 [Pixel MiPush](https://github.com/huaxianyan/PixelMiPush) 分别安装和更新：

- 框架负责共享连接、注册与推送记录、通知配置和消息处理，服务本身无需 Root 或 Xposed。
- 模块补充需要注入目标应用、系统框架或 SystemUI 的适配。启用方法、作用域和环境要求以模块文档为准。

模块不能给没有集成小米推送的任意应用补上小米推送能力。安装后应打开目标应用，确认它出现在注册应用列表，再从另一端发送真实消息验证。

### 为什么包名固定

客户端 SDK 通过 `com.xiaomi.xmsf` 查找共享推送服务，并检查服务版本。包名是接入协议的一部分，改成其他名称会影响服务发现。

中文显示名为「推送服务」，英文为 Pixel MiPushFramework。显示名与包名不必相同，也不能通过改包名让两份共享服务并行使用。

### normal 与 vc105

| 变体 | 用途 |
| --- | --- |
| normal | 默认选择，使用主要维护与验收的服务版本范围。 |
| vc105 | 面向明确依赖旧服务版本范围的接入方，保留兼容编号。 |

部分旧客户端会根据服务版本选择 `startService` 或 `bindService`。历史上有 COS 系统需要 vc105 的反馈，当前设备是否适用仍应实测，不能把 vc105 当作普遍更稳定的版本。

## 签名与迁移

同包名、同签名的更新可以覆盖安装，原有注册状态与推送记录随应用数据保留。本项目使用独立长期签名，与上游或其他来源的安装包可能不同。

**签名不同的安装无法直接覆盖，卸载会清除应用数据。** 迁移前先保存规则文件，并确认注册状态和推送记录是否有可用的备份与恢复方案。

仅保存通知规则不等于备份了注册数据。缺少完整备份时，应按原有数据可能丢失来决定是否迁移，并准备让目标应用重新注册。不要为了通过安装检查直接卸载现用服务。

本仓库使用独立版本线，旧的上游 0.3.x 安装包及其签名不属于同一更新源。通过 Obtainium 更新本项目时，正式版入口选择 normal，vc105 和测试版需单独选择。

Pixel MiPush 模块有自己的包名、签名和作用域配置。模块迁移按其仓库说明执行，不能用框架的更新步骤代替。

## 权限与后台运行

首次打开时按应用内向导完成授权。通知权限决定通知能否显示，电池优化等系统设置会影响调度与后台运行。

需要前台运行时，在「设置 → 高级配置」开启「推送服务保活」。前台服务也受 Android 的后台启动规则约束，不能把一个开关视为永久保活保证。

排障时检查是否有冻结、休眠或后台限制工具影响推送服务。目标应用与共享服务的权限、通知渠道和省电设置也应分别检查。

通常先按普通应用安装。只有目标应用的服务发现确实受系统应用列表限制时，再考虑系统应用部署，并预先确认备份和恢复方案。系统应用身份不能替代必要授权。

## 通知规则

在设置页选择「设置配置目录」，指定存放规则的目录。规则可以调整标题、正文、渠道与样式，也可能改变忽略、亮屏或弹出行为。

可从 [NihilityT/MiPushConfigurations](https://github.com/NihilityT/MiPushConfigurations) 按需选择规则。先阅读每份文件的 `description`，不要同时启用标记为互斥的白名单、黑名单或样式文件。

规则来自独立配置仓库，不等于本项目已对每种应用和消息完成验收。先启用少量规则，用一条真实消息对照结果，再逐步调整。

系统通知归属和部分会话样式还依赖 Pixel MiPush 的系统增强。框架中的规则、模块作用域和 Android 的显示模板共同影响最终效果。

## 常见现象

### 已连接，但某个应用收不到消息

「已连接」说明框架与推送服务器的连接状态，不代表所有应用均已注册。

1. 在应用列表确认目标应用已接入，必要时重新打开目标应用完成注册。
2. 检查通知权限、通知渠道、后台限制及可能忽略消息的配置规则。
3. 使用模块时，在模块管理器中检查是否启用及对应作用域。
4. 从另一端发送真实消息，再对照事件记录和日志定位。

本项目修复过网络切换后连接状态卡住的问题，但 SDK 的重连策略仍包含最高 5 分钟的退避间隔。它不是所有推送延迟的统一解释，也不能替代具体事件排查。

### 接入后，目标应用自己的推送服务停用了

部分客户端接入共享推送后，会停用自己的 `XMPushService`，改由共享服务处理。这与直接禁止应用全部后台行为不同，应结合注册和真实消息结果判断。

### 通知归属或样式与预期不同

先区分规则处理、模块增强和系统显示模板。当前普通通知路径的验收范围见 [Android 17 适配](ANDROID17-MIGRATION.md)，模块侧以其仓库文档为准。

旧通知可能保留创建时的点击入口和显示数据。改动后应重新发布通知，再判断效果。补收通知也可能显示较早的原始消息时间。

### MIUI、其他 ROM 与分身

本项目以 Pixel 为主要适配和验收对象。MIUI 等已内置官方同包名服务的系统，不建议直接用本项目替换内置服务。

上游曾记录过特定 ROM 的服务发现、禁用和通知限制，可在 [上游仓库](https://github.com/NihilityT/MiPushFramework) 查历史说明。这些记录不作为本项目对对应机型的新验收结论。

分身及多用户场景尚未验证，不在当前支持范围。其他机型请结合实际版本与日志判断，不能仅凭同一 Android 大版本推定兼容。

## 日志与反馈

通过「设置 → 获取日志」导出日志，在「设置 → 高级配置」中按需清理。推送凭据经过日志脱敏，设备标识等排障信息仍可能保留。

消息详情、配置内容和复制出的诊断数据不等同于已脱敏日志。公开分享前请检查消息正文、设备标识、凭据及自定义服务器信息。

提交 [Issue](https://github.com/huaxianyan/PixelMiPushFramework/issues) 时附上：

- 框架与模块版本、设备型号、Android 版本。
- 复现步骤、预期结果和实际现象。
- 相关权限、模块作用域及配置规则情况。
- 排除敏感内容后的日志，以及对应的时间范围。

已知边界、版本差异和近期验收结论见 [开发记录](STATUS.md) 与对应 Release 说明。
